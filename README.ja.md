# jsa-park — Claude Codeの長時間離席〜再開時のトークン消費を抑えるスキル

大量のコンテキストを使った Claude Code のセッションを1時間以上あける
と、プロンプトキャッシュが失効します。戻って一言送った瞬間、過去の
会話全体がキャッシュに登録し直され、重いセッションでは1ターンで
数十万トークンを消費することがあります。

jsa-park は、この再開時の消費を抑えるための Claude Code スキル2本組
です。離席の前にセッションを停め（park）、新しいセッションでは
引き継ぎメモだけを読んで再開（resume）します。

| スキル | 使う場面 | 何をするか |
|---|---|---|
| **`jsa-park`** | 離席の前 | 引き継ぎメモ `RESUME.md` を書き出す。決まったこと・保留中の提案・次にやること の記入欄も、その時点の会話内容から下書きされる |
| **`jsa-resume`** | 離席の後 | 新しいセッションで「再開します」と言うと `RESUME.md` を読み、決まったことと保留中の提案を区別して報告する。パークで節約できたトークン数もあわせて表示し、承認が出るまで作業を始めない |

[English README](README.md)

## インストール

```bash
git clone https://github.com/kansokusha2026/jsa-park.git
cd jsa-park
mkdir -p ~/.claude/skills && cp -r skills/jsa-park skills/jsa-resume ~/.claude/skills/
```

新しいセッションから自動的に有効になります。外すときは
`~/.claude/skills/` から2つのフォルダを削除してください。

## `jsa-park` の動き方

「離席します」と伝えるか、`/jsa-park` で発動します。

1. まず、パークが必要かどうかを判定します。1時間以内に戻る予定なら、
   キャッシュが生きていることが多いため、パークは不要と伝えて止まり
   ます。それより長い離席・就寝・利用上限での停止の場合に先へ進みます
2. 引き継ぎメモを下書きします。メモは2部構成で、前半が操作の記録
   （タスク・変更したファイル・作業の現在地）、後半が判断の記入欄です。
   「決まったこと」に入るのは利用者が明示的に承認した項目だけで、
   それぞれに承認発言の手がかりを添えます。承認が確認できない項目は、
   すべて「保留中の提案」に入ります
3. 確認を求めるのは1点だけです。「決まったこと」の中に、まだ提案の
   ままの項目が混ざっていないか
4. メモを保存して終わります。既存の `RESUME.md` は `RESUME.md.bak` に
   退避されるので、そのままセッションを閉じて構いません

## `jsa-resume` の動き方

同じフォルダで新しいセッションを開き、「**再開します**」と言うだけです
（`/jsa-resume` でも可）。スキルは `RESUME.md` を探して日付を確認し、
目的・決まったこと・保留中の提案・次にやること を報告して、節約
メーターを表示します。承認が出るまで作業は始めず、「保留中の提案」を
確定事項として扱うこともありません。この方式なら、過去の会話全体を
登録し直す代わりに、数千トークンで再開できます。

再開セッションは合図の一言から始まるため、タイトルが「再開」のままに
なりがちです。セッション管理ツールがある環境（Claude Code デスク
トップアプリ）では、ひとつ前のパーク済みセッションを元のタイトル＋
連番（「X」→「X(2)」→「X(3)」）にリネームして、セッション一覧の
つながりをたどれるようにします。セッションは自分自身をリネームでき
ないため、ひとつ前の分を次の再開時に直す方式です。CLI にはセッション
管理ツールがないため、この処理は行われません。

## 節約メーター

節約の効果は、パークと再開のたびに実測して表示されます。使い続ける
かどうかを、数字を見て判断できるようにするためです。

- `jsa-park` は、パークするセッションの最終コンテキストサイズを
  `RESUME.md` にスタンプします。読むのは `~/.claude/projects/` の
  ローカル記録だけで、標準ライブラリのみで動き、外部への送信は
  ありません
- `jsa-resume` は、そのスタンプと新しいセッションの実際の起動サイズを
  突き合わせ、差分を報告します

実例として、この機能を実装したセッション自体の実測値を示します。

```
=== jsa-park savings meter ===
parked session : 6297ec16  context 160,011 tokens after 77 requests (2026-08-12 08:47)
fresh session  : 96bd6731  cold start registered 78,680 tokens
context shed   : 81,331 tokens (-51%) — conversation history replaced by the handoff note
estimated savings (rate weights: 1h-cache write x2.0, cache read x0.1):
  per cold restart after a 1h+ break : ~162,662 input-token eq avoided
  per message from now on            : ~8,133 input-token eq lighter (vs. continuing the old session)
```

約8.1万トークンの会話履歴が、約1,500トークンの引き継ぎメモに置き
換わりました。残っているのは主にセッションの固定費（システム
プロンプト・ツール定義・プロジェクト設定）で、これはどのセッションでも
必ず読み込まれる分です。

推定値は金額ではなく「入力トークン何個分か」で計算しているので、
特定の価格を仮定していません。目安は、1時間キャッシュへの書き込みが
基本入力の約2倍、キャッシュの読み直しが多くのモデルで約0.1倍です。
ただし読み直しの料率はモデルによって違い、Claude Fable 5.1 は約0.025倍
です。そのためメーターは記録からモデルを読み取り、どの料率で計算したか
を report に明記します。`--cache-read-rate` `--cache-write-rate` で
上書きもできます。たとえば5分キャッシュを使っている場合、書き込みは
2倍ではなく1.25倍になります。

## 引き継ぎで何が残り、何が残らないか

AI にはセッションをまたぐ記憶がありません。毎回の応答は、そのとき
送られてきた文章（システムプロンプトと、それまでの会話の全文）だけを
見て作られています。前のセッションが文脈を踏まえた応答をできていた
のは、会話の全文が毎回まるごと送られていたからです。

引き継ぎメモに、この全文は入りません。数千トークンのメモに残るのは
次の4つだけです。

- 決まったこと（承認発言の手がかり付き）
- 保留中の提案
- 作業の現在地
- 次にやること

検討の経緯、読んだファイルの中身、失敗した試行は捨てられます。
それでも作業を続けられるのは、コード・ノート・Git の履歴といった
ファイルが手元に残っているからです。新しいセッションは、必要になった
ファイルをその場で読み直せます。

問題は、ファイルにも記録にも残らないものです。それが判断——どの案を
承認し、どの案を却下したか——です。書き残さなかった判断は新しい
セッションに伝わりません。よくあるのは、前のセッションで却下した
はずの案を、新しいセッションがもう一度提案してくるという形です。
記入欄を「決まったこと」と「保留中の提案」に分けているのも、
`jsa-resume` が承認が出るまで作業を始めないのも、この取りこぼしを
確認してから進めるためです。

## 公式の再開・要約との違い

Claude Code にも、長くなった会話を短くする機能があります。`/compact`
はそれまでのやりとりを要約に置き換えます。Pro / Max プランなら、
大きなセッションを長時間あけて開き直したときに「要約から続けますか」
と聞いてくれます。それで足りる場面では、公式の機能を使ってください。
このスキルは、その代わりになるものではありません。

選ぶときに知っておくと役に立つ違いが、2つあります。

### 要約がいちばん高くつくのは、久しぶりに開いた瞬間です

要約を作るには、AIがそれまでの会話を最後まで読み直す必要があります。
その読み直しは、会話が「読み込み済み」の状態（プロンプトキャッシュ）
で残っているうちなら、かなり安く済みます。ところが1時間以上あけると、
その読み込み済みの状態は消えてしまいます。消えたあとに要約を作らせる
と、会話の全文をもう一度、割引のない料金で読ませることになります。

厄介なのは、要約がいちばん欲しくなるのが、まさにその「久しぶりに
開いたとき」だという点です。長く離れていたから会話が長い。長いから
要約したい。でも長く離れていたせいで、要約する料金がいちばん高く
なっている。

`jsa-park` は、この作業を離席する前に済ませます。読み込み済みの状態が
まだ生きていて、会話の内容もAIの手元にあるうちに、メモを書き出して
しまう。同じ要約作業を、安いうちにやってしまおうという考え方です。

### 自動要約は「やったこと」を残し、「決めたこと」は残しません

自動で作られる要約は、作業の記録から組み立てられます。記録に残るのは
「やったこと」です。どのファイルを直したか、何を試して何が動いたか。
そこは正確に写ります。

写らないものがあります。あなたが「その案でいこう」と言ったのか、
「それはやめておこう」と言ったのか、です。却下した案も、検討したという
事実だけは記録に残ります。だから記録から要約を作る側から見ると、
採用した案と却下した案の区別がつきません。

これが抜け落ちると、次のセッションでこうなります。前回しっかり検討して
やめたはずの案を、AIが自信たっぷりに提案してくる。あなたはもう一度
同じ説明をして、もう一度断ることになります。引き継ぎで失うものの中で、
これがいちばん高くつきます。

`jsa-park` のメモは、「決まったこと」と「保留中の提案」を別の欄に分けて
います。そして書き出す前に、確認をひとつだけお願いします。「決まった
こと」の中に、まだ提案のままの項目が混ざっていないか。自動要約には、
この一手がありません。

## JSA との関係

[JSA](https://github.com/kansokusha2026/jsa) は、jsa-park の元になった
姉妹プロジェクトです。Claude Code のローカル記録を読んで、トークンが
どこで消費されているかを測る Python スクリプト3本で構成されています。
こちらはスキルではなく独立したスクリプトなので、Claude Code を起動
せずに（利用上限で止まっている最中でも）動きます。

jsa-park は単体で完結して使えますが、次のような場面では JSA が
役に立ちます。

- **導入する前に、自分に効果があるか確かめたいとき。**
  JSA の `jsa_gaps.py` は、あなたの記録から再開時の消費が実際に
  どれだけ起きているかを測り、引き継ぎメモを導入する価値があるかを
  判定します。このスキル2本は、その判定が「価値あり」だった場合の
  流れを自動化したものにあたります
- **パークし忘れて、セッションが失われたとき。**
  利用上限で止まった、クラッシュした、ウィンドウを閉じてしまった——
  そうなった後からでも、JSA の `jsa_handoff.py` が記録から引き継ぎ
  メモを組み立てられます。ただし、判断の記入欄は空欄になります。
  記録に残っているのは操作であって、判断ではないからです。できあがる
  メモは jsa-park のものと互換で、`jsa-resume` はどちらも読めます
- **測ってみたら、再開時の消費が主因ではなかったとき。**
  JSA の `jsa_routes.py` が、枠が減っていく他の経路（起動時の固定費、
  ファイルの流し込みなど）を順位づけし、改善候補を示します

数字で確かめてから使いたい場合や、上のような場面に当たった場合に、
JSA のほうも見てみてください。

## 注意

- パークしたあとの**元のセッション**には、何も送信しないでください。
  「戻りました」の一言でも、1時間以上あいていれば会話全体の再登録が
  走り、パークで避けようとした消費がそのまま発生します。戻ったときの
  合図は、必ず新しいセッションで「再開します」です。誤って送信して
  しまった場合でも、続きの作業は新しいセッションに移ってください。
  以後のやりとりが毎回軽くなります
- どちらのスキルも、キャッシュを温存し続けるものではありません。
  タイマーで短い送信を繰り返してキャッシュを延命する方法自体は
  成立します。その送信はキャッシュ読みの料率で課金されるので、
  読みが安いモデルなら、かなり長い離席まで冷たい再開より安く
  つきます。ただしパークより安くなることはありません。延命は
  会話を「持ち続けるための費用」を離席中ずっと払い続ける方法で、
  パークはその持ち物自体を降ろす方法だからです。消費が減るのは、
  古い会話を新しいセッションに持ち込まないためです
- スキルを入れると、トリガー用の説明文が全セッションの固定費に
  乗ります。2本あわせて1,000トークンに満たない量ですが、使う頻度が
  低い場合は差し引きを考えてください
- `RESUME.md` はプロジェクトのルートにできるため、誤って Git に
  コミットしやすいファイルです。`.gitignore` に `RESUME.md` と
  `RESUME.md.bak` を追加してください
- `RESUME.md` はプロジェクトのフォルダごとに1枚です。別のフォルダの
  プロジェクトを並行してパークするのは問題ありません。ただし**同じ
  フォルダで2回パークすると、前のメモは `RESUME.md.bak` に退避され、
  3回目のパークで消えます**（退避は1世代だけです）。古い方のメモから
  再開したいときは、`RESUME.md.bak` を `RESUME.md` に戻してから
  「再開します」と言ってください
- メモには作業内容やファイルパスが入り、認証情報や内部URLが混ざる
  ことがあります。共有する前に必ず中身を確認してください
- `/compact` `/clear` `/resume` の置き換えではありません。公式機能も
  試し、最適な方法を選択してください
